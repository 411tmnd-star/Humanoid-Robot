# RIGGING — Rigify Integration and MECH Layer Splicing

## Rigify Workflow Overview

Rigify is a Blender addon that generates rigged humanoids from a metarig
(a simple skeleton with special bone types and properties).

This project's workflow:

1. **Build the metarig** — simple bones marked with Rigify rig types
   (e.g., `basic.super_limb` for an arm, `basic.hinge` for elbow)
2. **Generate the rig** — Rigify creates DEF + CTRL bones automatically
3. **Add MECH layer** — insert the mechanical logic bones and constraints
4. **Test and export** — animate, bake, export to .glb, reimport and validate

## Rigify Rig Types Used

This project uses a subset of Rigify's rig types. Each joint's spec file
specifies which rig type to apply to its metarig bone.

### 1-DOF Hinges (no dedicated Rigify rig type)

**Used for**: 1-DOF joints (elbow, knee, PIP/DIP, thumb IP, ankle pitch)

No Rigify rig type for a single-axis hinge exists — confirmed against the
Blender 5.2 LTS Rigify install (`rigify.rigs.basic` contains only
`copy_chain`, `pivot`, `raw_copy`, `super_copy`; no rig source file anywhere
in the addon mentions "hinge"). A rig type named `basic.hinge` was assumed
in earlier drafts of this doc and of `elbow_forearm.md`; it does not exist
and has been removed from both.

**Metarig setup**:
- Single bone, no `rigify_type` assigned (left untyped)
- Parented into whichever Rigify-generated chain it attaches to (e.g. a
  hinge bone parented under a `limbs.super_limb`-generated upper arm)

**Bone layer setup**: Since there's no rig-type generation step, `CTRL_*`,
`MECH_*`, and `DEF_*` bones for the joint are created directly, by hand, in
the metarig/rig armature — not generated by Rigify.

**MECH layer**: `MECH_Elbow` (or equivalent) is wired between the hand-built
`CTRL_*` and `DEF_*` bones via the constraint stack specified in that
joint's own spec file (Limit Rotation, then Copy Rotation) — never via
Rigify rig-type generation.

---

### `basic.super_limb`

**Used for**: 3-DOF limbs (arm shoulder-to-wrist, leg hip-to-ankle)

**Metarig setup**:
- A chain of bones: shoulder → elbow → wrist (for arm) or hip → knee → ankle
  (for leg)
- Rigify properties: `limb_type = 'limb'` (or 'leg' for IK-by-default)

**Generated output**:
- DEF bones: shoulder, upper_arm, elbow, forearm, wrist
- CTRL bones: same names, plus IK/FK targets if IK is enabled
- Optional IK: Rigify auto-generates a 3-DOF or 2-DOF IK solver

**MECH layer**: Inserted between CTRL and DEF, one MECH bone per actuated
DOF (e.g., 3 MECH bones for shoulder's 3R, 1 for elbow's 1R, 2 for wrist's
2R).

---

### `basic.super_palm`

**Used for**: Palm metacarpals (MC2–MC5)

**Metarig setup**:
- One bone per metacarpal (MC2, MC3, MC4, MC5)
- Rigify properties: `rotation_axis = 'Z'` (or X, depending on orientation)

**Generated output**:
- DEF bones for each metacarpal
- CTRL bones for each metacarpal (usually minimal movement, mostly for
  cupping)

**MECH layer**: Often omitted for simple hands; palm motion is usually a
fixed offset or a single 1-DOF cupping joint per spec.

---

### `basic.super_finger`

**Used for**: Finger chains (PP → MP → DP per finger, or PP → IP for thumb)

**Metarig setup**:
- A chain of bones representing the phalanges
- Rigify properties: `bbone_segments = 1` (no bendy bones), rotation_axis = 'X'

**Generated output**:
- DEF bones for each phalanx
- CTRL bones for each joint
- Auto-generated PIP-DIP coupling if enabled

**MECH layer**: Can be used as-is (Rigify's coupling is good) OR replaced
with hand-built linkage if more control is needed.

## Pre-Generation MECH (Metarig Level)

Some MECH bones are added to the metarig **before** Rigify generates the rig.
They're not marked with Rigify rig types; instead, they're helper bones that
the CTRL/DEF generation then references or copies from.

**Advantage**: Rigify "sees" the MECH bones during generation and can parent
DEF bones to them automatically.

**Disadvantage**: If the MECH bone rolls or positions change post-generation,
it requires re-generating the rig.

**Example**: A wrist with two MECH bones (Flex and Dev) added before
generation, so Rigify's generated DEF_Wrist automatically inherits their
hierarchy.

---

## Post-Generation MECH (Constraint Overlay)

Other MECH bones are added **after** Rigify generates the rig. They sit in
a parallel bone hierarchy and feed into the DEF bones via constraints.

**Advantage**: MECH changes don't require regenerating the whole rig.

**Disadvantage**: The MECH hierarchy must be carefully constrained to DEF to
avoid conflicts with Rigify's own constraints.

**Example**: A shoulder with three MECH bones (Pitch, Roll, Yaw) added after
generation. Copy Rotation constraints link Rigify's CTRL → these MECH bones,
then these MECH bones → DEF bones.

**Precedence**: Rigify's DEF constraints should reference MECH, not directly
from CTRL. If Rigify generated a constraint that reads CTRL directly, it must
be overridden to read MECH instead.

---

## Constraint Override Process

After generating a Rigify rig:

1. **Identify the DEF bone** that needs MECH input (e.g., DEF_Elbow)
2. **Find its incoming constraint** (Rigify usually applies Copy Rotation from
   CTRL_Elbow)
3. **Replace the target**: Change the constraint's Target from CTRL_Elbow to
   MECH_Elbow
4. **Verify**: Rotate CTRL_Elbow → MECH_Elbow follows → DEF_Elbow follows

**Script approach**: Every constraint override is logged in a Python script
that can be re-run if the rig is regenerated. Never do this by hand in the UI
alone.

## Generating a Rigify Rig from Scratch

For a new joint:

1. **Create metarig bones** (in Rigify's metarig mode):
   - Add bones in the shape of the joint
   - Assign them Rigify rig types (via right-click menu or properties panel)
   - Set rotation axes and any other rig-type-specific properties

2. **Generate the rig**:
   - Rigify menu → Generate Rig
   - Metarig bones stay; new DEF+CTRL rig is created

3. **Add MECH bones** (pre- or post-generation per the spec):
   - Manually create MECH bones OR
   - Add them as part of the metarig before generation

4. **Override constraints**:
   - Replace CTRL references with MECH references
   - Add any custom constraints (limit rotation, pole targets, etc.)

5. **Test**:
   - Pose the CTRL bones
   - Verify MECH bones follow
   - Verify DEF bones follow
   - Confirm ROM and limits match the spec

## Bone Roll and Axis Orientation

Rigify assumes bones have correct rolls (orientation of local axes). Before
assigning a rig type:

1. Select the metarig bone
2. Open the Transform panel (press 'N' in 3D viewport)
3. Check the rotation values — they should be [0, 0, 0] (no prior rotation)
4. If they're not, reset: Armature → Recalculate Roll → X/Y/Z Axis (per spec)

After generation, verify that MECH and DEF bones have the same roll as the
metarig. If rolls diverged, the rig-type-specific rules applied an offset —
check the Rigify docs or re-roll manually per the spec.

---

## Bendy Bones

Rigify can use "bendy bones" (bones with multiple segments) for smooth
deformation. For robotic/mechanical rigs, disable bendy bones:

- Metarig bone properties: `Bbone Segments = 1`
- This ensures one DEF bone per joint, with sharp angles where they meet
  (matching mechanical reality)

For organic/anatomical rigs, bendy bones can approximate skin deformation.
The spec specifies per joint.

## Rigify Layer Organization

After generation, Rigify creates a DEF hierarchy. This project organizes it:

**Metarig** (source):

metarig (not exported)
├── Spine
├── Shoulder
├── Arm
└── Leg


**Generated DEF + CTRL**:

rig (generated by Rigify)
├── DEF
│ ├── Spine
│ ├── Shoulder
│ ├── Arm
│ └── Leg
├── MECH (added by this project)
│ ├── Spine
│ ├── Shoulder
│ ├── Arm
│ └── Leg
└── CTRL
├── Spine
├── Shoulder
├── Arm
└── Leg


Collections (Blender 4.0+) organize these into folders for clarity.

## When to Regenerate

If the metarig is changed (bones added, deleted, or rig types reassigned),
regenerate:

1. Delete the old rig (DEF + CTRL, but keep MECH if it's separate)
2. Modify the metarig
3. Generate the rig again
4. Re-apply MECH constraints (this is why they're scripted)

If MECH is post-generation, regeneration doesn't affect it — just re-run the
constraint-override script.

## Common Rigify Gotchas

**IK export bug**: Rigify's IK rigs sometimes export to glTF with incorrect
bone transforms. Always run the export → reimport validation check (§5,
docs/ENGINEERING_RULES.md). If the reimported rig looks wrong, either:
- Disable IK before export (use FK-only animations)
- Bake the IK to FK keyframes before export
- Use post-generation MECH + constraint override instead of Rigify's native
  IK

**Pole constraint axis**: Rigify's IK pole targets are sensitive to which
axis they're pointing along. The spec locks this; changing it requires
re-testing export behavior.

**Bendy bone deformation**: Bendy bones smooth deformation but add subtle
non-linear motion that surprises animators. Keep them disabled unless the
spec explicitly requires them.

## Validation Checklist

After generating or modifying a Rigify rig:

- [ ] Metarig bones have correct roll (X/Y/Z axes line up)
- [ ] Rigify rig-type assignments are correct
- [ ] Generation completed without errors
- [ ] DEF bones exist and are parented correctly
- [ ] CTRL bones are in the right collections
- [ ] MECH bones are added (pre- or post-generation per spec)
- [ ] Constraints are overridden (CTRL → MECH → DEF chain)
- [ ] ROM testing passes (pose CTRL, check MECH and DEF follow)
- [ ] Export → reimport validation passes
