# Phase v20 — leaner midsection, lightly thinned legs

Source v17 pipeline → `blender/robot_armature_v20.blend`, `blender/export/robot_v20.glb` (v18 / v19 files kept).
Reproduce: `python3 -I scripts/build/build_v20.py` (v17 → build_v18 with the contour / leg parameters → build_v19 hand joints → v20), then `export_v18.py`, `render_v18.py`,
`scripts/validation/v20_check.py <v19> <v20> <out.md>`, `V_WAIST=0.79 V_RIM=0.83 v18_verify.py <v17> <v20> <out.md> <glb> <roundtrip.log> <render dir>`,
`threejs/record_reference.py` + `threejs/run_viewer_test.mjs`, `thumb_curl_run.py`. Everything is in `proof/evidence_v20/`.

## What was wrong (measured on v19 before changing anything)

At the heights used since v18 the torso read waist / chest **0.859** (z 1.11) and rim / chest 0.921. But the narrowest point was higher, at z ≈ 1.21-1.22 (0.811), and below it the width
grew by 13 % to the hem (0.2274 → 0.2577 m). That swell below the waist is the "full stomach": the profile pinched and then bulged. A single waist ratio would not have fixed it; the narrowest point
had to move down to the waist and the width had to grow monotonically into the hips.

## Changes

| | v19 | v20 |
|---|---|---|
| waist / chest, z = 1.11 | 0.859 | **0.790** (target 0.78-0.80) |
| narrowest torso width | z = 1.21, 0.811 | **z = 1.11**, 0.790 |
| width z = 1.20 / chest (solved point) | 0.818 | 0.810 |
| rim / chest, z = 0.975 | 0.921 | **0.830** (below v19, so the hips are not widened) |
| profile | pinch then swell 13 % to the hem | narrowing to z 1.11, then widening monotonically (checked) |
| abdomen depth (front-back) at waist / chest depth | 0.867 | 0.758 (extra ×0.95 flattening over z 1.0-1.28) |
| chest half-width | 0.2805 m | 0.2801 m (unchanged, ±0.14 %) |
| pelvis shell half-width x / y | 0.2439 / 0.1720 m | 0.2196 / 0.1529 m (it follows the rim; hip sockets, yoke and every other piece unchanged) |
| thigh diameter top / bottom | 161.8 / 120.4 mm | 154.5 / 115.0 mm (−4.5 %, both ends) |
| shin diameter upper / ankle end | 125.8 / 88.1 mm | 120.2 / 88.1 mm (upper calf −4.5 %, ankle unchanged; ankle/upper 0.733, inside the 0.65-0.75 rule) |
| robot height, bounding box | 2.353 m, ±0.392 × (−0.202, +0.199) | 2.353 m, same; largest extent change 0.19 mm (torso back at chest, from the solver's 0.14 % chest re-balance) |

How: the contour solver (`v18_body.torso_contour`) now solves four heights at once (rim 0.975, waist 1.11, upper waist 1.20, chest) through smoothstep knots; an extra depth factor flattens the abdomen; `thin_legs` scales the thigh rings and the shin's proximal ring about their own centroids (lengths and centres untouched).
Because grooves, seam cutters, pelvis fit and visor projections all depend on the torso / shin surface, v20 is rebuilt through the same pipeline instead of patched on v19: the 1.5 mm grooves, the visor pocket and chamfer and the pelvis chassis are regenerated by the same code onto the new surface.
The default build_v18 behaviour (no options) is unchanged.

**First attempt, kept for the record:** rim 0.88 / upper waist 0.82 solved correctly but left a visible flare below the waist (0.79 → 0.88), the same kind of skirt-like swell in a milder form. The comparison render showed it; the final parameters are rim 0.83, upper waist 0.81.

## Not changed (proved, not assumed)

`v20_check.py` §2 against v19: all 184 bones identical (head, tail, rest-frame axes, max difference 0.0), all constraints / limits / locks identical (0 differences), modifier stacks identical, and the base vertices of the other 115 meshes (hands, fingers, head, neck, feet, visor, yoke, hip sockets, arms)
identical to 1.5e-8 m. Axis contracts and the 0.0000° zero-command deviation are therefore untouched.

## A weakness found in my own test, and fixed

The first Three.js run on v20 passed, but the control (the v19 GLB against the v20 reference) **also passed**: the compared boxes were dominated by extents that did not change (chest, head, hands), so the test could not see a 1.5 cm waist or 4.5 % thinner thighs.
I added thigh, shin and pelvis boxes and a torso **waist-band** measurement (x/y extent of the skinned vertices between z 1.05 and 1.17) to the Blender reference and the Three.js comparison; the control now fails and v20 passes. v19 was re-run under the stronger test (still passes); its committed `reference.json` was regenerated.
`v20_check.py`'s monotone-taper check starts at z = 0.98: at z = 0.97 the width is 0.6 mm *smaller* because the torso's bottom edge is bevelled, which is hem rounding, not a bulge.

## Limits

"Reads lean" is a visual judgement; the numbers show the narrowest point is at the waist, the swell below it is gone, and the abdomen is flatter, not that the proportions are final. The waist half-width at z 1.11 is 8.1 % smaller than v19's (0.2409 → 0.2213 m), and the lower torso is up to 10 % narrower at the hem, while the arms, shoulders and yoke are unchanged, so the shoulder-to-waist contrast is stronger; judge that in the renders.
The Three.js test is a software-rendered headless browser (loading, skinning, animation, geometry), not a GPU frame-rate test or your portfolio page.
